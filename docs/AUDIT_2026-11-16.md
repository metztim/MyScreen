# MyScreen Audit, November 2026

The recording core (one recorder, chunks streamed to one file) is sound. The audit found 25 defects in the code around it: error handling, the save path, app lifecycle, and feedback to the user. All 25 are fixed in the working tree and tested, and nothing is committed. Five larger items need a decision before anyone builds them.

## Decisions on larger changes

| # | Decision | Recommendation |
|---|---|---|
| 1 | Record H.264 instead of VP9 | Yes, after a live test |
| 2 | Controls outside the app window | Yes |
| 3 | Recordings readable by coding agents | Yes, in two steps |
| 4 | Upgrade Electron to 45 | Before the next release |
| 5 | Separate data folder for development | Yes |

Each one is described under [Feature candidates](#feature-candidates), [Agent integration design](#agent-integration-design), or [Open reliability problems](#open-reliability-problems).

## Fixes in the working tree

Every fix has a passing unit test or a scripted check of the real interface behind it ([Audit method](#audit-method)).

1. **Full disk froze the app:** when a write failed, the error was swallowed, every later write waited forever, and Stop hung on "Finishing up". The writer rejects the failed write, the recording stops with an error, and the part already on disk is offered for recovery.
2. **Closed window kept recording:** when the recorded window closed or a display was unplugged, the recording carried on with a frozen picture. The recording stops and saves up to that point, with a message that says why.
3. **Lost microphone went unnoticed:** a microphone that failed at the start showed a three-second notice while the status line still read "mic on"; one that disconnected mid-recording showed nothing. Both cases show an orange "No sound is being recorded" badge on the preview and a message that stays until dismissed.
4. **Lost camera froze the bubble:** a camera unplugged mid-recording left its last frame in the video. The bubble drops out and a message explains it.
5. **Capture sessions leaked:** switching sources quickly left three screen captures running instead of one, and a failed start (camera unavailable) left its screen capture running. Every acquired stream is released.
6. **Space started recordings by accident:** pressing Space on a focused row both opened that row and started a recording. Space starts a recording only when no control has focus.
7. **Reload stranded a recording:** Cmd+R during a recording (available in the released app's View menu) left the file open and invisible to recovery until the next launch. The file is closed and offered for recovery at once, the released app has no Reload item, and a crashed window reloads itself.
8. **Cmd+Q cut the last second:** quitting from the menu skipped the stop sequence. Quitting stops and finalizes the recording first, and a window that cannot answer cannot hold the app open.
9. **Two copies could run at once:** a second copy saw the first one's live recording as an unsaved leftover and could discard it. Only one copy runs per data folder.
10. **MP4 files carried a wrong label:** every MP4 was marked "Baseline, Level 3.0", which is the label for 720×576 video, on files up to 4K. Strict players can refuse such files. Files are encoded as High profile with the level the encoder picks (5.1 on a 3024×1964 test clip, about 16% smaller there).
11. **Long recordings failed to convert:** conversion decoded the whole file three times (a validation pass, a duration probe that could never find a duration, then the encode) and was killed after five minutes regardless of length. Conversion makes one pass, has no total time limit, and stops only an encoder that produces no output for 60 seconds.
12. **Half-written files appeared in the save folder:** a conversion that failed or was interrupted left a partial MP4 next to the finished recordings, and the WebM fallback had no duration or seeking. Outputs are written to a hidden file and renamed when complete, and the fallback is repaired the same way a normal WebM save is.
13. **Failed saves looked like lost recordings:** a save error flashed for three seconds and the app returned to "Ready". The error stays on screen, says the recording is safe, and the recovery sheet opens with a link to pick another folder.
14. **Library re-read every file on each launch:** thumbnails and durations were regenerated with one encoder process per recording after every restart. They are cached on disk, clips shorter than a second get a thumbnail, and files still being written are hidden.
15. **Dropbox tokens reached the interface:** the settings call returned the refresh token to the window, which never uses it. Tokens stay in the main process.
16. **Dead "Enable" button after a refusal:** once camera or microphone access is refused, macOS never asks again and the button did nothing. It opens the right pane in System Settings.
17. **Camera-only mode called a missing function:** every switch to camera-only raised an error in the background. Camera-only mode starts without it.
18. **Device menus went stale:** a microphone or camera plugged in after launch did not appear. The menus refresh on plug and unplug.
19. **Saved sheet showed a placeholder:** the thumbnail was a gradient, its play button did nothing, and the format label followed the setting instead of the file. It shows a real frame, plays the recording, and names the format on disk.
20. **Hardware encoding hid a trade-off:** the beta setting gives up crash recovery ([problem 1 below](#open-reliability-problems)) and its label did not say so. The label states the trade-off.
21. **Five smaller defects:** a possible hang while starting a camera overlay, long dashes in interface copy, the license field in `package.json` (MIT, while the repository is GPL-3.0), icon-only buttons without labels for screen readers, and unused save-dialog code.

## Open reliability problems

These need a recording on a real screen or a decision, so they are described and not changed.

1. **Hardware encoding is not crash-safe:** with the beta setting on, the recorder holds the video in memory until Stop. Confirmed in a test: after four seconds of recording, 1.2 KB was on disk, and the recovered file was empty. Decision 1 fixes it by changing how H.264 is recorded.
2. **Electron is eight major versions behind:** the app runs Electron 37.2.6, and `npm outdated` lists 45.3.3 as current. Electron supports the latest three, so the bundled browser engine receives no security fixes. The upgrade needs a signed build and a pass through the permission flow.
3. **One bitrate for every screen size:** recordings use 2.5 Mbps whether the source is 720p or 4K. I expect soft text during scrolling on large displays; it needs a side-by-side on a real screen before changing.
4. **Camera compositing draws more than it records:** the overlay redraws at the display's refresh rate (120 Hz on a MacBook Pro) for a 30 fps recording. I think this wastes GPU and battery; it needs measuring on a real capture.
5. **Development and the installed app share data:** both use the same settings and unsaved-recordings folder. With fix 9 the development copy also refuses to start while the installed app is open, unless it is given its own folder (`--user-data-dir`). A separate folder by default (decision 5) removes both issues.
6. **Dropbox upload restarts from zero:** one failed chunk fails the upload, and Retry begins again. The sign-in also listens on a fixed port (53682, the same one rclone uses), and the tokens sit unencrypted in the settings file. I'd propose retrying per chunk, picking a free port, and storing the tokens in the macOS keychain.
7. **Quit ends a recording without asking:** the recording is finalized and offered at next launch, with no confirmation and no normal save. I'd propose a "Stop and save" or "Keep recording" prompt.
8. **Save path has no unit tests:** conversion and export live in `main.js` and were verified through the interface only. Moving them to their own module would let the test suite cover them.

## UX findings

The interface is clean and its states are clear. Each item here needs a design choice before any change.

1. **Recording the full screen records MyScreen too:** the app window stays in the picture, and reaching for Stop becomes the last seconds of every recording. I think this is the largest gap against Loom. Decision 2 addresses it.
2. **Three timers and two sets of controls:** while recording, the preview badge, the floating bar, and the bottom bar each show the time, and Pause and Stop both appear twice. One set is enough.
3. **Saving blocks the app:** the conversion sheet is modal, so a second recording waits for the first to convert. Decision 1 makes saving close to instant.
4. **Large minimum window:** 1140×740 fills most of a 13-inch screen. A compact layout (controls only, preview optional) fits a recorder better.
5. **Source picker takes two clicks:** select, then "Select". Double-click works but nothing says so. A single click could choose and close.
6. **Settings sit in odd places:** the countdown is under Output, and "Floating controls" is under Advanced.
7. **System audio reads as a fault:** "Not available on this Mac" suggests the Mac is the problem. Either build it (see feature 3) or say "Not supported yet".
8. **One message at a time:** a new notice replaces the one on screen, so a routine message can overwrite an error. A short stack would fix it.
9. **Recovery sheet shows a placeholder:** the unsaved recording has no real thumbnail or duration.
10. **Keyboard and screen-reader gaps:** sheets do not trap focus, and the picker has no arrow-key navigation.

## Feature candidates

These are ideas, none committed. Items 4 to 6 are in the Notion backlog.

1. **H.264 recording with instant save (decision 1):** record H.264 inside a WebM container, then copy the video into an MP4 on save and convert only the audio. In a test the chunks reached disk every second (so crash recovery works) and a recording became an MP4 in 0.25 seconds, against a full re-encode today. Quality from the hardware encoder at 4K needs a live comparison first.
2. **Controls outside the window (decision 2):** a menu bar item with the timer, global shortcuts for start, pause, and stop, and hiding the app window while a full-screen recording runs.
3. **System audio:** recent macOS versions can capture it without a helper, and newer Electron releases expose that. I have not verified it on this app; it depends on the Electron upgrade.
4. **Microphone level while recording:** a small live meter, so a silent recording is visible before it is finished.
5. **Automatic updates:** release builds already produce the files an updater needs (`latest-mac.yml` and a zip).
6. **Library actions:** show in Finder, rename, delete, copy the Dropbox link, upload an older recording, and search.
7. **Trim:** cut the start and end of a recording before sharing.
8. **Transcript and title per recording:** covered in the next section, because agents need the same thing.

## Agent integration design

A screen recording with narration is a fast way to brief a coding agent: "watch what happens when I click this, then fix it". An agent cannot watch video, so the recording has to become things it can read. I'd propose building that in two steps, the second on top of the first.

**Step 1, files next to each recording:** after a save, MyScreen would write a small folder for the recording.

1. A transcript of the narration with timestamps, made on the Mac.
2. Key frames: one image at each moment the screen changes, sized for a model to read.
3. A summary file with the title, date, duration, recorded app, and the paths of the other two.

Any agent with file access can use these without extra setup, and the library gains search and readable titles from the same data. The Saved sheet would get a "Copy for agent" button that puts the summary file's path on the clipboard.

**Step 2, an MCP server:** a small server bundled in the app that Claude Code and Codex start on demand. It reads the same folders, so it works while MyScreen is closed, and it would offer these tools.

1. `list_recordings`: recent recordings with title, date, and duration.
2. `get_recording`: the summary and full transcript of one recording, with "latest" as a shortcut.
3. `get_frames`: images for a time range or at the screen changes.
4. `search_recordings`: text search over transcripts.

A settings row would show the one-line command that registers the server with each agent. Starting and stopping recordings from an agent (so it can record a demo of its own change) is possible later; I'd keep it off by default, since it lets a program start screen capture.

The transcription engine is an open choice between a bundled speech model and the speech recognition built into macOS. Neither is tested here.

## Areas checked and sound

The audit checked these areas and found no defect.

1. **Chunk ordering:** writes are chained, so the file on disk matches capture order under uneven write latency. Covered by a test.
2. **Pause accounting:** paused time is excluded from the duration, including a stop while paused.
3. **Window security settings:** context isolation, the sandbox, and the content security policy are all on.
4. **Dropbox app key in the source:** it is a public identifier for a sign-in flow that needs no secret.
5. **Dependencies:** `npm audit` reports no known vulnerabilities in the shipped packages.

## Audit method

The audit read all application code, ran the unit tests (12 before, 19 after), and drove the real interface through its debugging port with simulated screen, camera, and microphone streams, in a separate data folder and save folder. Real screen capture, the installed build, and a Dropbox upload were not exercised, because they need permissions and accounts a scripted run does not have. A live recording on the built app is the remaining check before a release.

## Code changes by file

The fixes touch five modules, the interface files, and the three test suites.

- `recording-writer.js`: per-entry `error` set by a persistent stream listener; `write` resolves on the write callback; `finalize` on a failed entry marks the sidecar `interrupted` and rejects; `releaseAll()`.
- `recording-engine.js`: streams join `_ownedStreams` as soon as they exist; `_watchTrack` and `_onSourceEnded`; `hasAudio`; `error` events carry `phase` and a `released` promise; `_playVideo` waits on `play()`.
- `main.js`: `exportRecording`, `writeAtomically`, `remuxContainer`, `convertWebMToMP4` (High profile, stall timer only); single-instance lock; close fallback timer and `forceQuit`; `releaseOpenRecordings` on main-frame navigation and renderer loss; `before-quit` routes through the window close flow while a recording is open; `buildAppMenu`; `rendererSettings`.
- `library-store.js`: `index.json` beside the thumbnails, `metaFor`, `_prune`, first-frame fallback.
- `ui/controller.js`: generation counters for preview and camera sync; `_showSaved`; `reason()` strips IPC wrapping from error text; toast kinds.
- Tests added: `test/library-store.test.js` (uses the bundled ffmpeg), plus cases in the engine and writer suites.
- H.264 test recipe for decision 1: `MediaRecorder` with `video/webm;codecs=h264,opus`, then `ffmpeg -i in.webm -c:v copy -c:a aac -movflags +faststart out.mp4`.
